# JSON Diff View

**Compare two JSON documents side by side, privately in your browser.**

A dependency-free, static web app for developers, API users, QA engineers, and anyone who needs to find changed JSON values quickly. No signup, analytics, external scripts, upload, or backend.

## Features

- Paste JSON in two side-by-side editors or open local \`.json\` files. Imported documents are syntax-checked and require confirmation before replacing existing contents; stale asynchronous file loads cannot overwrite edits, swapped documents, cleared editors or a newly loaded sample.
- Compare object keys and nested structures with exact \`$\` paths.
- Highlight additions, removals, and changes in aligned before/after columns. Filter recorded changes by a case-insensitive JSON path substring and by change type; navigate 100-result pages without rendering all 5,000 entries simultaneously.
- Load an illustrative sample, swap documents, or clear editors.
- Copy the full JSON change report or download it in **JSON** or **CSV** format. CSV is UTF-8 with spreadsheet-formula neutralization; exports include recorded changes regardless of UI filters or pages.
- Export a **standards-based RFC 6902 JSON Patch** as a bare JSON array, through clipboard or a downloadable `.jsonpatch` file. Select **Before → After** for forward changes or **After → Before** for a reverse/rollback patch. Optionally add `test` operations before each generated removal or replacement to detect unexpected values at those paths.
- Preview applying any imported or generated JSON Patch to a **detached copy** of the selected Before or After document. Inspect the resulting JSON plus a **separate source-to-preview impact report** with added/removed/changed counts, path/type filters, 100-row pages and full-report clipboard, JSON and CSV exports. Download the result or explicitly send it to the opposite editor for comparison. **Use generated patch** automatically selects the appropriate source for forward or reverse output.
- Inspect patch instructions before applying them: a read-only, 100-row-paged operation ledger shows instruction order, type, JSON Pointer path, `from` source, shortened value preview and basic shape warnings. Filter by operation and path. The ledger does not apply operations or claim semantic validity.
- **Step-by-step preview:** choose an integer N from 0 to the patch length to preview the source document after exactly the first N operations; navigate through intermediate states with Previous/Next or select **View step** directly from the patch operation ledger. Each step also displays a **per-operation structural diff** between the immediately previous and current snapshots, with 100-row pagination. The result is an isolated, read-only JSON view (up to 2 MiB) that can be copied or downloaded as a direction- and step-specific JSON checkpoint. Its per-operation change report can likewise be copied in full or exported as JSON/CSV, including truncation and step-source metadata. The remaining operations are not executed and failed earlier operations abort that step without displaying a partial result.
- **Compare two patch checkpoints:** choose any steps A and B with `0 ≤ A ≤ B ≤ patch length`, and inspect the net structural differences between those intermediate documents. Both checkpoints are independently replayed from the same selected source, so earlier `test`/`move`/`copy` semantics are respected. Filter the recorded changes by JSON path/type, navigate 100-row pages, and copy or locally download the complete recorded range report as JSON/CSV.
- **Generate a checkpoint-range JSON Patch:** derive a new standards-compliant `.jsonpatch` array from the two computed checkpoint documents (rather than copying original operations), with optional `test` guards before generated remove/replace instructions. Copy or download this patch independently of report filters. Both **start checkpoint (patch input)** and **end checkpoint (expected result)** are also available as independent, copyable/downloadable JSON documents named with the source and step number. The patch must be applied to the **step A checkpoint document**, not directly to the original source when A > 0.
- **Portable checkpoint bundle:** download the two complete endpoint JSON documents, the generated patch and the original source/step metadata as a single versioned `*-bundle.json` file. On another browser, **Import checkpoint bundle** loads the starting checkpoint into Before, the ending checkpoint into After and the patch instructions into the patch editor. Replacing existing content needs confirmation; importing a bundle never executes its patch or submits data to a server.
- **Expected-result comparison:** after explicitly previewing the patch on a detached source, choose **Compare with opposite editor** to see whether its output matches the expected Before/After editor **structurally**. Mismatched JSON paths, values and add/remove/change counts are shown with filters, 100-row paging and full JSON/CSV report downloads. No editor is changed, and no imported bundle is applied automatically.
- **Failed-operation diagnosis:** when the full preview fails on an RFC 6902 operation, the error identifies the **1-based operation number, type, path/from and reason**. The last successful prefix (0..N−1) is independently replayed from the original source, shown read-only, and can be copied, downloaded or opened in step inspection. The failing operation is never included in this checkpoint, even for a `move` that removed a source before failing at the destination.
- **Failure reproduction bundle:** explicitly copy or download a versioned `*-repro.json` file with the original document, instructions through the failure, exact failing index/reason and the last good checkpoint. The same file also includes an **isolated one-operation patch** for reproducing the failure against the last good checkpoint. Alternatively, **Isolate failed operation** replaces the selected source editor with the last good document and the patch editor with only that operation, after a confirmation; the opposite document is untouched and no patch is run automatically.
- **Import failure bundle:** select **Isolated failed operation** (default) to load the last-good document and one failing instruction, or **Full prefix through failure** to load the original JSON with all instructions through the failed step. The corresponding Before/After source and patch editor are populated only after explicit overwrite confirmation when needed. The opposite editor is preserved; import does not replay any instruction.
- **Verify imported failure (opt-in):** after importing a reproduction, explicitly click **Verify imported failure** to replay its completed prefix on a detached copy, compare the recomputed last-good checkpoint with the stored one, and check that both the full prefix and the isolated operation fail at their expected positions. The UI distinguishes **REPRODUCED**, **INCONSISTENT BUNDLE** and unavailable verification; the recorded error wording is compared separately.
- **Forensic verification report:** inspect every recorded discrepancy between the recomputed and stored last-good checkpoints, filter by JSON path and change type, and navigate 100-row pages. Copy or download the complete **verification JSON** (including expected/found operation position, reproduced status, isolated failure and reason-text checks) or download **CSV** containing every recorded checkpoint mismatch, independent of filters.
- **Portable verification evidence:** after an explicit replay, download a versioned JSON evidence file containing the recorded failure source and instruction metadata, full behavioral findings and every recorded checkpoint difference (not the original input document or executable patch). Use **Open saved evidence** to reopen the findings in the existing paged, filterable read-only viewer on another browser. Archived findings are prominently labeled **SAVED EVIDENCE (NOT REVERIFIED)**; opening them never executes the patch or writes to an editor.
- **Compare archived evidence:** select two saved evidence JSON files (baseline and candidate) and compare their recorded failure metadata, reproduction findings, and checkpoint difference entries. Recorded checkpoint rows are grouped by JSON path and change type rather than report row number, avoiding false drift from reordering or newly inserted rows. Filter the differences, navigate 100-row pages and copy/export a complete JSON or CSV comparison. Different failure identities are explicitly flagged; neither file is replayed or authenticated.
- **Classify recorded evidence drift:** the comparison summarizes changes by **failure metadata**, **reproduction findings**, and **checkpoint differences**. It distinguishes different failure identities, newly reproduced failures, failures that are no longer reproduced, behavioral changes without an overall status transition, checkpoint-only changes, metadata-only differences and unchanged archives. A dedicated **Area** filter narrows the displayed report while leaving complete exports unaffected; the JSON export includes the detailed assessment and the CSV source label includes its classification.
- **Review an archive timeline:** import **2–10** saved verification evidence files simultaneously. Filenames are sorted in ascending codepoint order (use date-prefixed filenames such as `2026-11-22-01-evidence.json`); the app never guesses chronology from timestamps. Choose **Consecutive archives** to compare each pair of neighboring files, or **Every archive vs first baseline** to compare each later file against the earliest. Both modes display claimed reproduction state transitions, drift classification, cross-case warnings, checkpoint changes and truncated-record warnings, and export the entire archived analysis as JSON or formula-safe CSV. These are read-only comparisons of historical claims and cannot prove a bug fix or regression.
- **Failure identity inventory:** every loaded 2–10-file history groups archived snapshots using the exact same failed-operation identity used by two-file drift classification: source, failed operation index/type/path/from (not error wording or replay mode). The **Recorded failure identities** panel shows snapshot counts, recorded reproduction claims, first/last file and the number of contiguous filename-ordered runs, so a case that reappears after a different failure is visible. Select **Focus history** to filter transitions involving that case (including explicitly labeled cross-case boundaries), or **First vs last** to inspect its earliest and latest saved snapshots. The complete history JSON contains case IDs, snapshot memberships and contiguous runs; transition CSV includes both case IDs, and a dedicated formula-safe Cases CSV exports the full identity inventory. These are unverified archived claims, not an assertion that two sources truly share the same underlying root cause.
- **Per-case longitudinal progression:** **View case progression** follows consecutive appearances of a single recorded failed-operation identity, even when unrelated failures intervene in the filename-ordered history. Each comparison uses the same bounded two-archive drift engine and records baseline/candidate files and indices, claimed reproduction transition, drift classification, number of intervening other-case snapshots and truncation. **Inspect same-case change** opens the existing path-level inspector for that pair; a separate **Case progression CSV** exports the complete selected progression. The full history JSON includes bounded `case_progressions` for every recorded identity, independent of the primary adjacent/first-baseline history mode.
- **Recurring evidence change paths:** each analyzed history now aggregates repeated changes across its comparison pairs, grouping checkpoint row/value subfield changes by normalized report path and change type. The most frequently affected 200 paths are ranked by how many comparisons contain them, with total recorded occurrences, area/path filters, an unfiltered CSV export and **Inspect latest change** navigation to the corresponding archived pair. Use **View path history** to open a focused timeline of every archived comparison that changed the selected path, including filenames, drift classification, per-comparison occurrence counts and direct buttons to inspect those comparisons. Download the selected path timeline as a separate formula-safe CSV. The complete history JSON includes the bounded hotspot summary, including truncation flags; comparisons that hit the 5,000-difference cap are reported as lower-bound counts. This is historical evidence-path analysis, not a claim of live source-document mutations.
- **Compare any two loaded history snapshots:** after building a 2–10-file history, use **Earlier snapshot** and **Later snapshot** to select any chronological pair, even when files are not adjacent. The custom pair opens in the existing drill-down with filters and complete export; it does not alter the history's consecutive/first-baseline mode or its overall JSON/CSV transition summaries. Re-selecting either file invalidates a pending custom comparison.
- **Inspect an individual history transition:** click **Inspect transition** on any comparison row (adjacent pair or first-baseline pair) to examine its complete recorded path-level evidence differences with path, difference-type and area filters and 100-row paging. Copy or download the selected pair's full unfiltered, bounded change report and drift assessment as JSON, or download all recorded differences as formula-safe CSV. The app reads only that pair's local files when requested; viewing a pair never executes instructions or changes document editors.
- Import a local `.jsonpatch` or `.json` file into the patch editor. The import validates that it contains an array of at most 5,000 operations and respects the 2 MiB file limit; **it does not execute the patch or change either document**. If patch text is already present, replacing it requires confirmation. Switching to a newly generated patch cancels any unfinished import so an older file cannot overwrite the selected patch.
- Keyboard shortcut: **Ctrl+Enter** (Windows/Linux) or **⌘+Enter** (macOS).
- Responsive layout with keyboard-accessible controls, light and dark themes.

## Portable editing workspace

Use **Save workspace** to download a versioned `json-diff-view-workspace` v1 JSON file. Unlike checkpoint bundles, this preserves the exact **raw text** of the Before, After and JSON Patch editors, including incomplete or invalid JSON drafts. It also saves the selected patch source, forward/reverse patch direction, both guard settings and the step/range inputs. Generated reports, execution results, imported forensic archives and private browser state are not included.

Use **Open workspace** to stage a local file for **review before restore**. The preview shows current and saved editor byte lengths, whether each of the four sections differs, and how many patch/range options have changed, without displaying sensitive draft contents. Selectively restore **Before**, **After**, **JSON Patch** and/or **patch/range settings** with the individual checkboxes. **Apply selected sections** requires explicit confirmation whenever a selected section changes current content; unchecked sections are preserved. **Cancel restore** makes no edits. Editing current values during an open preview invalidates it; pending file reads and competing document/patch/bundle imports cannot overwrite a newer selection. After a successful restore, **Undo restore** is enabled for a single in-memory undo of exactly the fields that changed, rather than replacing entire editor sections indiscriminately. An explicit confirmation precedes undo; untouched sections and other changes remain intact. Editing a restored field disables undo, and programmatic changes to restored values are checked again before undo to prevent clobbering newer work. A subsequent successful restore replaces the previous undo checkpoint. Undo does not survive a page reload and is never persisted in the workspace file.
  
Restore **never parses or validates the editor JSON**, executes a JSON Patch, automatically compares documents, uploads a file or sends data to a server. The outer workspace schema and option types are validated, with an **8 MiB** file limit and **2 MiB per editor**. After a confirmed selective restore, stale comparison and patch previews are cleared; re-run Compare JSON or Preview applying patch only when ready.

### Manual in-tab session snapshots

Use **Save in tab** to keep a named copy of your current raw editing workspace (Before, After, Patch and range/guard settings) without downloading a file. The **Manual session snapshots** panel stores up to **8 snapshots** with a total serialized-memory cap of **24 MiB**, per-snapshot limits inherited from portable workspace files, and an explicit snapshot selector. **Preview restore** opens a stored snapshot in the same selective restore panel used for imported files, with confirmation before any selected editor value changes. **Download snapshot** saves an individual snapshot using the standard versioned Workspace v1 JSON format; **Delete snapshot** frees memory without touching current editor contents.

**Rename selected** changes a stored point's display name without changing its ID or serialized workspace. **Update selected from editors** re-captures the complete current raw workspace into the selected in-tab point, retaining the same name, ID and snapshot slot. Both require confirmation. Updating validates the normal workspace size rules and preflights total memory consumption **before** replacing data; an invalid or over-capacity update leaves the original point intact. Updating or renaming a point invalidates a stale collection-import preview and, when applicable, a staged restore of that point. These actions never replace the current editor contents or execute a patch. Download the old point first if a previous version must be retained: this is an intentional overwrite, not a version history.

Snapshots exist **only in the memory of the current browser tab**: no `localStorage`, IndexedDB, cloud sync, background saving or automatic uploads. Closing or refreshing the tab loses them. Download individual snapshots before closing if they are needed later; the browser controls whether downloads persist. A snapshot preview is read-only until the user applies it, and selecting a new file or an updated editor cancels stale previews. Stored snapshots may contain sensitive documents, so clear unwanted snapshots and handle downloaded files accordingly.

### Compare saved in-tab workspace snapshots

**Compare saved snapshots** selects two named in-tab snapshots (or a saved snapshot and the current unsaved workspace) and inspects raw editor contents without restoring or executing patches. It compares exact **raw** Before/After/Patch strings, even when their JSON is incomplete, and summarizes sizes, line counts, shared head/tail lines, and patch settings. The changed middle now uses **bounded longest-common-subsequence (LCS) alignment** to distinguish **Added**, **Removed** and **Changed** rows when insertions or deletions shift line positions. Neighboring removed and inserted lines form a changed row, while unchanged lines matched by LCS are skipped. For bounded browser work, LCS is limited to **1,000 middle lines per side and 400,000 matrix cells**; larger regions use an explicitly identified **positional fallback**. The report includes each editor's alignment strategy and change counts, so fallback counts are not mistaken for optimal line diffs. The preview retains **up to 180 changed rows per editor and 240 characters per line**. This is still a raw-text line comparison, not a semantic JSON change report or patch replay; omitted rows are counted. Contiguous changed lines now receive a **1-based change hunk ID**: each exact aligned unchanged line separates adjacent hunks. The report records the total hunk count for each editor and retains **up to 48 bounded hunk summaries per editor**, with earlier/later line ranges, added/removed/changed counts, total changed rows and previewed rows. The **Change hunk** selector navigates directly to hunks with recorded previews, coordinated with the editor and change-type filters; other hunks are still reflected in aggregate totals but may have no selectable preview because of the 180-row cap. LCS boundaries are exact for the chosen LCS alignment; positional-fallback boundaries are descriptive and may not correspond to optimal textual edits. Hunk identity is local to each editor and comparison and is not a stable document ID. For later hunks beyond the initial 48 summaries or 180 rows, **Inspect any change hunk** accepts an editor and the exact 1-based hunk number (up to that editor's recorded count), then re-runs the same bounded line alignment against the selected snapshot pair **on demand**. A new independent inspection shows the requested hunk's earlier/later ranges, full added/removed/changed counts and up to **180 changed-row previews with 240 characters per line**; it reports any omitted rows. A captured current-workspace comparison is checked for staleness before opening or exporting an inspection, and any new comparison or snapshot change clears previously opened details. **Hunk JSON/CSV** exports contain only the selected hunk's bounded text previews and count/range metadata, not the complete drafts. The inspector now supports **Previous hunk / Next hunk** navigation and **0, 1, 2, 3 (default), or 5 lines of unchanged context on each side**. Unlike guessed line offsets, context is taken from actual equal-line matches produced by the chosen LCS/fallback aligner, with trimmed shared document prefix/suffix restored at the first/last hunk. Context rows are labeled separately from Added/Removed/Changed and do not consume the 180 changed-row cap; there can be **at most 10 additional context rows**, each still clipped to 240 characters. The JSON/CSV reports explicitly label these contextual rows and the requested/available context counts. Choosing a listed hunk from the main selector also populates its number in the on-demand inspector for direct opening. For a positional-fallback editor, hunk numbers still reflect the explicitly disclosed fallback alignment. **Changed-row paging** now makes any part of a long hunk inspectable: specify a 1-based page or use **Previous page / Next page** once a hunk is opened. Each page re-runs the existing bounded alignment, counts the entire hunk but retains only the selected **180 changed-row window**. The inspection marks the page number, total pages and first/last 1-based changed-row indices within the hunk, rejects nonexistent pages and supports both saved-to-saved and saved-to-current snapshots with the same staleness guards. Up to five matched context lines *before* a hunk are included **only on page 1**; up to five *after* are included **only on the final page**, so middle pages cannot misrepresent remote context as adjacent. JSON/CSV downloads include this page metadata and only the selected bounded window, never complete editor drafts. This navigation is explicit and does not store full diff traces across pages.

Choose **All sections** or a specific editor/settings area, then filter **Added / Removed / Changed** to focus on a change type. **Comparison JSON** and formula-safe **Comparison CSV** include bounded recorded snippets, hunk IDs and alignment metadata (plus summary counts and line ranges), but do not embed complete editor drafts. Snapshots are read only when the user explicitly compares; changing, deleting, renaming, updating or importing snapshots invalidates the prior comparison to avoid stale results. Draft snippets in exports may still contain confidential text; handle them accordingly.

### Compare saved snapshots against the current unsaved workspace

The two snapshot comparison tools now also offer **Current unsaved workspace** as a selectable source or destination. One saved snapshot is sufficient: compare a previously saved draft to the current Before/After/Patch texts and patch/range settings without consuming another snapshot slot. **Compare from** and **Compare to** determine the direction independently of chronological order. Selecting the current workspace on both sides is disallowed.

The app captures the complete current raw workspace as a transient, local Workspace v1 serialization **only when the user clicks Compare**, then runs the existing bounded raw-line or opt-in structural JSON comparison against the selected saved snapshot. It does not persist that captured workspace, run any JSON Patch or change an editor. Subsequent changes to editor text or controls invalidate comparisons involving the current workspace, without clearing unrelated saved-to-saved reports. Before rendering filtered previews or downloading either report, the current editor/option values are rechecked even when programmatic file imports did not dispatch browser input events, preventing stale results from being represented as current. Rerun the comparison to include newly edited drafts. Exports remain bounded previews and do not contain the complete unsaved document.

### Opt-in structural JSON comparison of snapshots

Alongside the always-available raw draft comparison, **Compare JSON structure** performs an **explicit, read-only structural comparison** of the JSON values stored in the selected two snapshots. The Before, After and JSON Patch editor drafts are parsed **independently**; invalid or empty drafts are reported for their individual editors without preventing comparison of other valid editors. A JSON Patch editor draft is compared **as JSON data**, never executed or validated as an operation sequence. Both snapshots and the live editor contents remain unchanged.

The existing deterministic engine compares object keys by name and arrays by index (not element identity). It limits work to 5,000 structural changes, 100,000 visited values and 200 levels of nesting. The new UI displays each editor's parse/error status and added/removed/changed counts, with **up to 250 bounded change previews per editor**, **240 characters per value** and **300 characters per path**. It indicates omitted rows and truncated comparison counts as **lower bounds**, and offers editor/type/path filtering with 75-row paging. **Structural JSON/CSV** exports contain these limited previews and descriptive metadata, **not whole JSON values or documents**. Previews and filenames may still contain sensitive text. Snapshot updates, deletion, renaming, import and pair changes invalidate the previous reports.

### Export and import an entire snapshot collection

**Download all snapshots** exports named manual in-tab snapshots as one versioned `json-diff-view-snapshot-collection` v1 JSON file, containing embedded **workspace v1 objects** (not a JSON Patch script). **Open snapshot collection** first validates and **stages** all entries in a read-only selection table showing the original names, decoded workspace sizes and whether a name already exists. Choose individual snapshots, or **Select all**/**Select none**, and switch **Append**/**Replace** while the preview remains open. Capacity is recalculated for the **selected subset** before the import button is enabled. Zero selection and over-capacity combinations are rejected without touching the list; duplicate names in Append are allowed but explicitly disclosed as separate entries. **Import selected snapshots** then requires confirmation of the selected count, action and resulting memory usage. **Append** preserves current snapshots; **Replace** discards them and atomically loads only selected entries. Canceling, selecting another collection or mutating current snapshots invalidates the previous preview, and replacement cancels a staged restore referring to a removed snapshot. Malformed or oversized imports cannot partially mutate the store.

A collection contains 1–8 named workspaces; decoded workspace text remains subject to **8 MiB per snapshot** and **24 MiB aggregate in-tab memory**, and the outer collection file is capped at **32 MiB**. Oversized pretty-printed exports fall back to compact JSON; if even compact encoding exceeds 32 MiB, export is refused rather than silently losing data. A collection import never touches the current Before/After/Patch editors or runs a patch. All snapshot names and editor drafts may contain sensitive material; files remain local unless the user shares them. In-tab snapshots still disappear on reload unless the collection is downloaded.

### Recoverable pre-restore backups

During **Review workspace restore**, **Download complete current-workspace backup before applying** is selected by default. When the user confirms a restore with that option enabled, the app first initiates a local download of the complete original workspace as `json-diff-view-before-restore.json`, **before** replacing any selected fields. If preparing that backup fails the restore is canceled without modifying editors. **Back up current workspace now** lets the user export the same pre-restore snapshot independently of applying a restore. The file uses the normal `json-diff-view-workspace` v1 schema and preserves every raw editor draft and option, including sections not selected for replacement.

This file can later be reopened via **Open workspace** after a browser reload, unlike the one-step memory-only **Undo restore**. Browser download prompts and restrictions mean an initiated download is **not proof that a file was saved**: check your Downloads folder before relying on recovery. The default backup can be unchecked; no backup is made in that case. Backups remain local, contain potentially sensitive editor data, and are never uploaded.

Workspace files can contain sensitive editor contents and should be stored and shared accordingly. This is a manual local save/restore feature, not autosave or cloud synchronization.

## Open locally

Open [index.html](index.html) in a modern browser, or serve this folder over HTTP:

\`\`\`sh
python3 -m http.server 8000
\`\`\`

Then visit \`http://localhost:8000\`. Browser security policies for ES modules may prevent some browsers from opening the app directly from a \`file://\` URL; serving over HTTP is the reliable method.

**Deployment:** Host the repository root on any static web host (for example GitHub Pages, Netlify, or Cloudflare Pages). GitHub Pages must be enabled separately in repository settings if desired.

## Comparison semantics

- Object keys are compared by name, regardless of their order in the original JSON.
- Arrays are compared **by index**, not by record ID or edit distance. Inserting an item near the front can produce several changed-index entries.
- Numbers, strings, booleans, and \`null\` compare by value. Unlike text diffs, \`1\` and \`1.0\` represent the same JSON number.
- Added or removed nested objects/arrays appear as a single path containing the full value, rather than one row per descendant.
- The **visual change report** is still a descriptive list of before/after values and is **not itself a patch**. On-screen path/type filters and pagination only change the displayed rows; **Copy change report**, JSON/CSV report downloads and JSON Patch exports use the complete recorded comparison, not the current filtered page. A report truncated by the 5,000-change safety limit remains marked as truncated.
- The **separate JSON Patch export** emits RFC 6902 `add`, `remove`, and `replace` operations in either direction, independently computed from the actual Before and After values; opt-in **guarded generation** inserts `test` checks immediately before `remove` and `replace` (but never generates `move` or `copy`). The **import/apply** editor additionally understands external `test`, `copy`, and `move` operations. Object paths use JSON Pointer escaping (`~0` for `~`, `~1` for `/`). The root document path is the empty string.
- Array changes are index-based: common positions are compared, excess trailing entries are removed from highest index to lowest, and new trailing entries are added in increasing index order. This does not infer semantic moves or record IDs.
- A guarded patch compares each value that will be removed or replaced with the expected source value (Before in forward mode, After in reverse mode). It is **not** a full-document concurrency guard: newly added properties, array appends, and unrelated changes are not protected. No guards are added when generating a pure-add patch.
- If the transformation needs more than 5,000 operations, or if the serialized patch exceeds 2 MiB, the tool refuses to export a potentially incomplete or unimportable patch. Forward and reverse exports use direction-specific filenames (for example, `changes-after-to-before.jsonpatch`). Guarded generation also enforces the preview engine's shared 100,000-node/200-level test budget. Guard operations count toward the 5,000-operation limit. Review any patch before applying it to production data.
- The step preview shares the real patch engine's RFC 6902 semantics, order and `test` budget. Each request recomputes a detached prefix from the selected source, without storing prior intermediate states. The per-step change report independently recomputes the previous prefix and compares two detached snapshots; if its bounded comparison fails, the intermediate JSON remains available and the unavailable effect is explicitly shown. A successful `test` or no-op may produce an empty per-step change report. Editing the source or patch, importing or generating new instructions, switching the selected source, or editing the selected step discards the previous step result and disables exports until another successful preview. Checkpoint downloads and full step-impact downloads are local only; the shared 8 MiB report export limit applies, and the step JSON itself remains capped at 2 MiB. It does not replace the full patch preview or transfer any document to the editors.
- Expected-result comparison treats JSON objects with reordered keys as equal, but array positions and primitive values must match. It compares the actual detached result to the opposite editor and only reports **MATCH** when the entire bounded structural comparison contains no changes. Invalid expected JSON, excessive comparison complexity or a failed patch preview never produce a false success. Source, patch or expected-editor changes make previous mismatch reports stale and disable exports. The complete recorded mismatch report, rather than only the visible filtered page, is copied/exported.
- Checkpoint bundle format is `json-diff-view-checkpoint-bundle` version `1`. The bundle is capped at **8 MiB**, while its embedded documents and patch must each fit the **2 MiB** editor/import limit and patch operation count must not exceed 5,000. Unknown format versions or malformed metadata are rejected. In-flight local bundle imports cannot overwrite intervening editor changes, patch edits or newer imports. The embedded patch is not automatically applied or semantically executed on import.
- A checkpoint-generated patch represents the **net transformation** between the selected endpoint documents. It may omit canceled-out operations, replace moves with ordinary add/remove/replace instructions, and does not guarantee identical intermediate behavior. Guarded exports test only removed/replaced values, not additions or unrelated changes. Patch generation is separately bounded to 5,000 operations and 2 MiB; if it exceeds those limits, the range report and endpoint-document exports stay available. Checkpoint JSON is constrained to the 2 MiB editor/import limit, with compact formatting used if pretty-printing would exceed that size. Endpoint export actions refuse stale range selections and never modify either source editor.
- Range comparison shows **net state changes**, not necessarily every intermediate mutation: two opposite operations can cancel out. It executes both prefixes on detached copies, does not run operations after the selected end step, and refuses invalid steps, failed earlier operations, oversized endpoint documents or excessive structural diff complexity. Reports may be truncated at 5,000 changes and exports are subject to the existing 8 MiB cap. Editing the selected source, patch text, or step numbers invalidates the previous range result.
- **Inspect patch operations** is read-only and flags obvious malformed instruction shapes (including missing pointers/values and unsupported operations); it cannot predict whether paths or array indexes resolve on the selected source. Changing the patch text, clearing the editors, importing another patch, or using a new generated patch discards the earlier ledger.
- Both custom-pair and per-transition drill-down reopen only the two selected local file handles on demand and recomputes the same bounded archive-only diff used by the timeline summary. Changing the selected history files or starting another history analysis invalidates any pending drill-down read, clears its results, and prevents stale detail exports. Full detail JSON includes both archive metadata, reproduction claims, descriptive drift classification and the recorded structural difference report. Detail CSV contains the full recorded path differences, not the displayed filtered subset. The shared 8 MiB report-export cap still applies.
- A custom snapshot comparison requires the earlier file's index to be lower than the later file's index. It is labeled `comparison_mode: "custom"` in detail JSON, with explicit 1-based baseline/candidate snapshot indices; CSV source metadata and local download names also identify the chosen pair. Custom comparisons do not affect the historical transition analysis. Selecting another pair cancels any in-flight pair read before its results can be shown, and neither file is executed or uploaded.
- The saved-evidence history comparison mode is stored explicitly as `comparison_mode` (`adjacent` or `baseline`) and the first file as `baseline_file`. Both the JSON and CSV exports preserve mode information so comparisons to the first snapshot are not mistaken for consecutive temporal transitions. Changing comparison mode invalidates displayed history and any pending detail request without changing source editors.
- Each hotspot now also records bounded `transition_details` for every affected comparison (at most nine in a 10-file history), including source/target archive filenames, drift classification, occurrence count, same-case status, truncation and a specific example report path for drill-down. These details are included in full history JSON and in the selected-path CSV. A path's occurrences are not counts of independent failures; differing failure identities and truncated reports require human review.
- Same-case progression compares successive occurrences of one recorded identity rather than globally adjacent archives. Gaps do not imply that the failure was absent, only that the intervening archives recorded another identity. Each progression reuses the descriptive drift classification and never runs a patch. Longitudinal `case` detail exports retain explicit source/candidate snapshot indices so nonadjacent comparisons cannot be mistaken for a main history transition.
- Case grouping is limited to the specific recorded failing instruction identity and does not prove the same root cause, environment or source code version. The IDs (`case-1`, etc.) are only stable within the current filename-ordered analysis, not across separate histories. The independent contiguous-run count shows when a case disappears and returns after one or more other identities. First-vs-last comparisons can bridge such gaps intentionally; transition filtering preserves boundaries as marked different-case comparisons. All analysis is local and read-only.
- Hotspot frequency measures **how many selected archived comparisons recorded a normalized evidence path**, not how often a source property changed or how many independent reproductions succeeded. An individual path is counted once per comparison, even when several difference rows share it. When the top-200 display is truncated, the full number of distinct recorded paths is retained; when a pair's structural diff was truncated, hotspot counts can be incomplete. This analysis does not execute JSON Patch or authenticate saved evidence.
- History analysis rejects duplicate filenames or fewer than two/more than ten archives, enforces the existing 8 MiB per-file bound and applies the same structural comparison limits to every consecutive pair. It reads the files locally, in deterministic filename order, and exports all transition summaries even when the UI classification filter hides rows. Different failure identities are reported, not incorrectly combined into an unbroken progression. Neither history imports nor exports execute any patch or alter editor data.
- Drift classification is deliberately **descriptive rather than a confirmed regression/fix**: archived results may come from different environments, engine builds or manually edited files. A change in recorded failure identity is not treated as an apples-to-apples regression. Newly reproduced/no-longer-reproduced states are review prompts, not conclusions. Scope totals and changed finding paths cover **recorded** differences only, and when the 5,000-change comparison cap is reached the assessment is explicitly marked truncated.
- Offline evidence comparison parses both archives using the existing versioned schema and 8 MiB input caps, then computes one bounded structural diff across their recorded metadata, behavioral findings and checkpoint differences. Comparison paths refer to the normalized evidence report, not to the original source document. The baseline/candidate selection is explicit; filters affect only visible rows, while JSON/CSV exports retain all recorded changes and are limited to 8 MiB. A zero-change archive comparison means the recorded content is equivalent, **not** that either archived claim has been independently verified. A separate failure-identity warning is shown when the two archives refer to different failing operations.
- Portable evidence uses `json-diff-view-verification-evidence` version `1`, a maximum 8 MiB file, up to 5,000 recorded differences and explicit validation of result fields and counts on import. It stores the recorded result **as a claim, not an authenticated proof**; users must re-import the original failure bundle and explicitly replay it to independently confirm a saved finding. Diff values can still contain sensitive JSON fragments, even though the full source and executable patch are excluded. Opening the archive does not start a replay.
- Verification results are computed only after an explicit user click, not during imports or application startup. The verification JSON includes the individual behavioral checks and complete bounded checkpoint difference report; the checkpoint CSV contains only the recorded structural differences, with a source label identifying the failing operation. Exports retain truncation indicators and the existing 8 MiB download cap. If the selected source, patch text, replay mode or editor contents become stale, the report and export actions are invalidated.
- An imported failure bundle is **not verified when parsed or imported**. Optional verification reconstructs the last-good checkpoint from the recorded original document and completed instructions, rather than trusting the stored checkpoint; it uses the same RFC 6902 engine and bounded structural comparison as the normal UI. A match means the behavior is reproducible with this engine, **not** that the source or metadata is externally authenticated. A changed source, patch, replay mode or selected base invalidates the imported verification target; no replay modifies an editor.
- Failure reproduction bundles use `json-diff-view-failure-bundle` version `1`. Their original source, prefix-through-failure and last good checkpoint must each fit the standard **2 MiB** limit, while the complete portable file is capped at **8 MiB**. They contain full input JSON and may disclose sensitive data if shared; the app never uploads them. The isolated patch is exactly the failed operation, not a substitute for the original multi-operation context. The isolation action requires explicit user confirmation before replacing the selected source/patch editors. The importer rejects unknown format versions, inconsistent operation counts and differing isolated/prefix operations, with editor-size limits on every embedded document/patch. It never executes the imported instructions or verifies that the supplied last-good snapshot and reason are truthful; use explicit preview to reproduce the behavior. Asynchronous imports are abandoned after intervening edits, mode changes or newer imports.
- Failed-operation diagnosis is available only when parsing succeeded and the application engine reached an operation. The last successful prefix is replayed on a fresh detached clone to avoid leaking a partially mutated `move` state; its preview is capped at 2 MiB. If replay or size limits prevent reconstruction, the failed operation remains identified while the checkpoint controls stay disabled. Source or patch edits invalidate the diagnosis and disable its exports.
- The Patch preview accepts **`add`, `remove`, `replace`, `test`, `copy`, and `move`**. `test` checks the value at its JSON Pointer without modifying it. Object property order is ignored, while array order matters. A missing path or failing assertion aborts the entire preview and leaves the original document unchanged. JSON comparisons share a bounded 100,000-node work budget. `copy` reads an existing `from` pointer and inserts a detached value at `path`; `move` removes the source before inserting it at the destination, so array indexes are evaluated after removal. Moving into the source's own descendant is rejected; moving onto the same path is an existing-path-checked no-op. Removing the document root as part of a move is unsupported. Malformed pointers and array indices are rejected.
- An empty path targets the document root for add/replace. Removing the root document is unsupported. Arrays may be appended with \`-\` in an add operation; array indexes are otherwise canonical decimals.
- Example guard: `[{"op":"test","path":"/version","value":1},{"op":"replace","path":"/version","value":2}]`; the replacement executes only if the test matches. Example array move: `[{"op":"move","from":"/items/0","path":"/items/2"}]` (the destination is interpreted after removing index 0). Example copy: `[{"op":"copy","from":"/settings","path":"/settingsBackup"}]`.
- Patch application never mutates the input JSON value. Object property reads require own properties; assignments use safe property definition for keys such as \`__proto__\`. Invalid operations abort without returning a partially modified document.
- The result preview is capped at **2 MiB** and is not written into either editor until **Send result to After** or **Send result to Before** is clicked, depending on the selected patch source. The impact review compares the original selected source against the computed result, not the operations in the patch. It can be truncated at 5,000 recorded differences; if its 100,000-node/200-depth comparison limit is exceeded, the result remains available but the impact review is marked unavailable. Filters only affect visible impact rows, not the copied impact report. Importing a patch performs file reading and shape/size checks only; semantic validation occurs during explicit Preview. In-flight file loads are ignored when the patch editor changes, preventing stale asynchronous imports from replacing typed instructions. If the destination editor already has content, the tool requests confirmation before replacing it. Switching the preview source invalidates the previous preview, and changes to the selected source or patch text invalidate result transfer/download.

- Input is limited to **2 MiB per editor**. Traversal has limits of 100,000 visited nodes, nesting depth 200 and 5,000 recorded differences. The table displays up to 100 rows per page, with filters operating on those recorded differences; a truncated report is explicitly marked as such.
- Long values in the visual table have shortened previews; copied and downloaded reports contain full recorded values.
- CSV exports use CRLF rows, UTF-8 BOM, and complete JSON-serialized values in `before_json`/`after_json` columns (so explicit `null` differs from a missing value). The `report_truncated` and `source` columns provide context. User-controlled cells beginning with spreadsheet formula prefixes are escaped before quoting. No data is uploaded; downloads are created locally. Downloads refuse files exceeding **8 MiB** rather than silently truncating them. An empty CSV report contains a header row only.

## Privacy

All parsing, comparisons, and file reads occur on your device. The application makes no network requests itself. If you host it publicly, the hosting provider may log requests for the static application files, but the pasted JSON is not sent to that host.
